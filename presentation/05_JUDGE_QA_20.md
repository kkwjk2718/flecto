# 심사위원 예상 질문 20개와 답변

**답변은 현재 근거에 맞춰 사용한다. 구현·실행이 없는 상태에서 완료형으로 읽지 않는다.**

## Q01. 그냥 AI 에이전트가 대신 해주면 안 되나요?

**답변**

대신 처리하는 것이 목적이라면 적합할 수 있습니다. FLECTO는 사용자가 직접 내용을 확인하고 수정하는 화면에 집중합니다. 준비된 현재 화면의 반복 조작을 일반 코드로 처리하고, 두 사이트에서 같은 조작 방식을 쓰며, 원본이 바뀌면 연결을 다시 검증하는 구조입니다.

**보여줄 근거·제한**

현재 화면 추가 계획 요청 차단·원본 저장·두 사이트 시연. 아직 실행하지 않았다면 목표로 표현한다.

## Q02. 기존 접근성 위젯과 다른 점은 무엇인가요?

**답변**

글씨·대비 같은 표시 설정만이 아니라 사용자의 목표에 필요한 입력과 선택을 단계로 묶고 실제 원본 기능에 연결하는 것을 목표로 합니다. 기존 도구 전체가 이런 기능을 제공하지 못한다고 일반화하지는 않습니다.

**보여줄 근거·제한**

같은 과제의 원본/재구성 화면, 현재 구현 범위.

## Q03. 이 아이디어가 세계 최초인가요?

**답변**

세계 최초라고 주장하지 않습니다. 맞춤형 인터페이스에는 관련 접근이 있습니다. 이번에는 원본 기능 연결, 검증된 구조 재사용, 직접 조작 경험을 제품으로 구현하고 확인하는 데 집중합니다.

**보여줄 근거·제한**

특정 연구와 직접 비교하려면 원문 확인 필요. 이번 통합은 신규 선행연구 조사가 아니다.

## Q04. AI를 사용하지 않고 템플릿만 만들면 안 되나요?

**답변**

템플릿은 화면 형태이고 처음 보는 페이지의 필수 입력·안내·실행 대상을 찾고 묶는 일은 별개입니다. FLECTO에서는 그 연결 계획에 AI를 사용하고, 이미 확인한 구조는 검증 후 재사용하려 합니다.

**보여줄 근거·제한**

새 구조에서 실제 계획 생성·현재 요소 연결 검사. 숨은 정답은 금지.

## Q05. 데모 사이트에 맞춰 미리 정답 화면을 만든 것 아닌가요?

**답변**

원본 사이트는 테스트 환경입니다. 제품에는 숨은 정답 메타데이터나 사이트명별 완성 화면 분기를 넣지 않는 기준을 세웠습니다. 다른 요소 ID·필수 입력·중복 버튼의 변형과 두 번째 사이트로 검증해야 합니다.

**보여줄 근거·제한**

실제 코드·holdout·변형 결과. 검사 전에는 통과했다고 답하지 않는다.

## Q06. 고령자에게 정말 쉬운가요?

**답변**

고령자를 고려한 큰 글씨·큰 버튼·명확한 단계로 설계했지만 그것만으로 사용성 효과가 입증되는 것은 아닙니다. 이번 체험자는 심사위원과 주변 참가자이며, 실제 고령자 평가는 후속 과제입니다.

**보여줄 근거·제한**

참가자 구성·도움 제공·완료·오류 기록. 고령층 효과 수치 없음.

## Q07. 왜 크롬 확장인가요? 설치가 어렵지 않나요?

**답변**

현재 로그인된 원본 탭의 기능에 연결하는 기술을 검증하기 위한 초기 형태입니다. 설치 자체도 진입 장벽이 될 수 있습니다. 이번 체험은 준비된 팀 기기에서 하며, 서비스 내장형 도입은 이후 검토합니다.

**보여줄 근거·제한**

실제 설치·프로필 조건 공개. 설치 용이성이 증명됐다고 하지 않는다.

## Q08. 저장된 비밀번호를 읽나요?

**답변**

읽지 않는 원칙입니다. 원본 로그인 화면에서 Chrome 자동완성으로 합성 계정을 사용하고 로그인 이후 시작합니다. 로그인·OTP 화면에서는 분석과 캡처를 멈추며 비밀번호를 모델로 보내지 않습니다.

**보여줄 근거·제한**

로그인 중 수집 중지·sentinel·로그 검사. 개인 Chrome 프로필 공개 금지.

## Q09. 개인정보는 어디로 가나요?

**답변**

모델과 공유 캐시는 개인 입력 대신 허용한 공개 페이지 구조를 받도록 설계했습니다. 실제 입력·선택·확인 값은 브라우저에서 원본에 연결하고, 광고에는 그 데이터를 넘기지 않습니다. 실제 전송 경로는 검사 결과의 범위를 밝혀야 합니다.

**보여줄 근거·제한**

전송 스키마·캐시·로그·가림·광고 분리 검사. 100% 보안 보장 금지.

## Q10. 잘못된 버튼을 누르거나 동의가 빠지면요?

**답변**

실제 요소가 유일한지, 같은 문서와 폼인지, 필수 항목·고지가 보존되는지 실행 전에 확인합니다. 연결이 모호하면 추측하지 않고 원본에서 계속하도록 합니다. 사용자가 선택하지 않은 동의는 자동으로 체크하지 않습니다.

**보여줄 근거·제한**

중복 버튼·필수 누락·동의·stale 테스트.

## Q11. 신청이 중복되거나 결과가 안 오면요?

**답변**

제출 중 반복 클릭을 막고 결과가 불명확하면 자동 재제출하지 않습니다. 원본 내역을 확인하도록 안내합니다. 테스트 서버의 중복 방지까지 확인하되 모든 외부 서비스의 exactly-once를 보장하지는 않습니다.

**보여줄 근거·제한**

연타·Enter·응답 유실·원본 저장 건수 검사.

## Q12. 3초 안에 항상 되나요?

**답변**

3초는 목표이며 아직 일반적인 성능 보장이 아닙니다. 실제 사용 가능한 시점까지 cold/warm/시각 보완을 나눠 측정합니다. 한 준비 요청에서 10초가 되면 계속 기다리게 하지 않고 원본으로 돌아갈 수 있게 합니다.

**보여줄 근거·제한**

실측 전체 시도·성공/실패/timeout·시간 정의.

## Q13. 페이지가 바뀌면 캐시는 깨지지 않나요?

**답변**

깨질 수 있으므로 현재 필수 항목·고지·폼·대상과 다시 대조합니다. 구조만 재사용하며 값과 강좌·정원은 현재 원본에서 읽습니다. 일치하지 않으면 재분석하거나 안전하게 멈춥니다.

**보여줄 근거·제한**

필수 항목·고지 변경·옵션 변경·warm 상태.

## Q14. 모든 웹사이트와 캡차도 지원하나요?

**답변**

아닙니다. 이번 범위는 두 테스트 사이트와 명시한 일반 폼·메뉴·검증된 React 입력입니다. 결제·첨부·CAPTCHA 우회·접근 불가능한 프레임 등은 제외하고 원본으로 안내합니다.

**보여줄 근거·제한**

지원/미지원 사양. 거부 성공을 작업 완료율에 합산하지 않는다.

## Q15. 자체 모델을 서버에 올린 건가요?

**답변**

제품 추론은 우리 기기에서 실행하는 Codex 런타임을 통해 원격 모델을 호출하는 계획입니다. 모델 가중치를 로컬에서 학습·호스팅한 것과 다릅니다. 개발 모델도 제품 추론과 분리합니다.

**보여줄 근거·제한**

실제 model-lock·런타임 연결. 현재 모델·설치 상태 미확인.

## Q16. 로딩에 광고를 넣으면 일부러 느리게 만들 유인이 있지 않나요?

**답변**

그래서 준비가 끝나면 광고 시간을 채우지 않고 즉시 없애는 정책을 제품에 넣었습니다. 재사용이 빨라지면 광고가 안 뜨는 것이 정상입니다. 광고는 성능 최적화의 보상 지표가 아닙니다.

**보여줄 근거·제한**

2.9초·3.1초·10초·광고 오류·완료 즉시 제거 검사.

## Q17. 광고 수익으로 비용을 감당할 수 있나요?

**답변**

현재 계약·정산·비용 자료가 없어 확정할 수 없습니다. 시연 광고는 동작 검증이며, 실제 정산 가능한 노출과 단가, 기간 후원 가능성, 신규 추론·재사용·지원 비용을 함께 확인해야 합니다.

**보여줄 근거·제한**

사업 가설·단위경제성 변수. 5원 등 과거 일화를 단가로 쓰지 않는다.

## Q18. 공공기관이나 기업이 도입할 이유가 있나요?

**답변**

복잡한 신청의 완료·문의·지원 부담을 줄일 수 있는지가 가치 가설입니다. 원본 기능을 유지하는 인터페이스라는 점을 제안할 수 있지만, 실제 운영 데이터와 담당자의 요구·배포 책임을 확인해야 합니다.

**보여줄 근거·제한**

기관 고객·계약 확보를 주장하지 않는다. 파일럿 조건과 인터뷰 계획.

## Q19. 현재 어디까지 검증했나요?

**답변**

현재 릴리스 등급과 같은 빌드의 근거를 기준으로 답하겠습니다. [실측값 넣기: ACTUAL_GRADE_AND_EVIDENCE]이며, [실측값 넣기: UNVERIFIED_SCOPE]는 아직 확인하지 못했습니다. 계획 목록과 통과 결과를 구분합니다.

**보여줄 근거·제한**

현재는 제품 NOT_RUN이므로 그 상태를 말한다. 문서 검사 수를 제품 PASS로 쓰지 않는다.

## Q20. 다음 단계에서 무엇을 할 건가요?

**답변**

두 사이트의 정확한 동작과 오류 처리를 먼저 확보하고, 고령자를 포함한 대상 사용자 평가와 기관의 제한적 파일럿을 검토합니다. 이후 관리 도구·SDK·다른 환경은 실제 수요와 운영 조건이 확인된 뒤 단계적으로 확장하겠습니다.

**보여줄 근거·제한**

로드맵의 진입 조건. 날짜·매출·배포를 약속하지 않는다.

## 공통 대응 원칙

확인된 범위부터 답하고 모르는 부분은 미검증이라고 말한다. 새 수치·비교 우열·계약을 즉석에서 만들지 않는다. 답변을 회피하기보다 실제 화면·원본 결과·시험 범위를 제시한다. 상세 정책은 [주장 근거표](../evidence/00_CLAIM_LEDGER.md)와 [공개 점검표](../evidence/02_PUBLISH_CHECKLIST.md)를 따른다.
