# 데모 큐시트 — 원본 기능과 차별화 증거

**현재는 실행 계획이다. 실제 앱·검증 빌드·계정·캡처가 준비됐다고 가정하지 않는다.**

## 1. 시연 전 한 번 확인

검증 빌드·제품 등급, 실제 Codex 접근, 테스트 서비스·DB·포트, 별도 Chrome 시연 프로필, 합성 계정 원본 로그인, 개인 알림 제거, cold/warm 조건, 광고 시연 라벨, 원본 복귀, 10초 종료를 확인한다.

시연 상태 표시에는 LIVE CODEX / CACHE / FIXTURE / REPLAY를 사용한다. 고정 응답 테스트 결과를 실제 모델 성능처럼 설명하지 않는다. 실제 브라우저 화면을 생성 이미지나 목업으로 대체해 기능이 작동한 것처럼 보이지 않게 한다.

## 2. 기본 순서

| 장면 | 발표자가 말할 것 | 조작 | 확인할 근거 |
|---|---|---|---|
| 1. 원본 | ‘원하는 것은 구매 혜택 신청입니다’ | 원본 첫 화면에서 확인된 작업 선택 | 원본 URL·로그인 상태·실제 메뉴 |
| 2. 화면 준비 | ‘필요한 입력과 버튼을 다시 구성합니다’ | FLECTO 목표 선택 | 현재 요청·실제 대기·모드 표시 |
| 3. 직접 조작 | ‘입력과 동의는 사용자가 합니다’ | 합성 주문 정보 입력·원문 확인·동의·검토 | 실제 입력이 원본 요소와 일치 |
| 4. 원본 완료 | ‘완료 표시는 원본 처리 결과를 확인합니다’ | 명확한 신청 버튼 → 결과·원본 신청 내역 | 실제 저장값·건수. UI 성공문구만으로 끝내지 않음 |
| 5. 추가 요청 차단 | ‘준비된 현재 화면 안의 수정에는 새 계획이 필요하지 않도록 했습니다’ | 새 테스트 흐름의 READY 후 계획 endpoint만 차단 → 수정·제출 | 차단 범위·추가 계획 요청·원본 응답 |
| 6. 다른 사이트 | ‘같은 템플릿을 문화센터에도 적용합니다’ | 강좌·시간 선택·동의·검토·원본 신청 | 다른 사이트의 실제 결과 |
| 7. 변경 대응 | ‘원본이 바뀌면 오래된 연결을 쓰지 않습니다’ | 별도 변형 페이지 또는 필수 입력 추가 | stale 거부·재분석·필수 항목 보존 |

짧은 발표에서는 1–4를 우선하고, 5–7은 검증된 녹화 또는 Q&A에서 보여줄 수 있다. 녹화 여부를 반드시 표시한다. 5는 이미 제출한 결과를 다시 바꾸는 것이 아니라 **별도 새 테스트 흐름**에서 수행해 중복 신청을 피한다.

## 3. 광고는 실제 조건에서만

3초보다 빠르게 준비되면 광고가 안 나오는 것이 정상이다. 보여주기 위해 cache를 일부러 느리게 만들지 않는다. 별도 장애 주입 시험에서만 3초·10초 동작을 보여주고 ‘fault injection / 대기 처리 테스트’로 표시한다.

광고가 나타나도 준비가 끝나면 즉시 사라지는 것을 확인한다. 광고 영역이 제출 버튼으로 교체되어 오클릭을 유도하지 않는지 본다. 실제 후원 계약이 없으면 시연 광고 라벨을 유지한다.

## 4. 실패 대응표

| 발생 상황 | 행동 | 발표 문장 |
|---|---|---|
| 실제 모델 10초 내 미완료 | 기다림 종료, 원본 계속하기. 반복 요청을 무한 실행하지 않음 | ‘지금 요청은 준비를 끝내지 못했습니다. 원본으로 돌아갈 수 있게 처리합니다.’ |
| 원본 신청 응답 불명확 | 자동 재제출 금지, 원본 내역 확인 | ‘결과를 확정할 수 없어 중복 신청 대신 원본 내역을 확인합니다.’ |
| 캐시 무효화 | 현재 필수 항목을 읽고 재분석 또는 안전 복귀 | ‘구조가 달라졌으므로 예전 연결을 그대로 쓰지 않습니다.’ |
| 로그인 만료 | 원본 로그인 화면, 분석·캡처 중단 | ‘로그인은 원래 서비스에서 진행하며 FLECTO는 비밀번호를 읽지 않습니다.’ |
| 네트워크 장애 | 검증된 local fixture 또는 실제 녹화가 있으면 라벨하고 전환 | ‘이후 화면은 고정 응답 검사/녹화이며 LIVE가 아닙니다.’ |
| 두 번째 사이트 미완성 | 첫 사이트 검증 범위만 보여줌 | ‘문화센터는 아직 확인하지 못한 부분이 있어 확장 목표로 남아 있습니다.’ |
| 프레젠테이션 영상 실패 | 실제 앱 또는 정적 설명으로 진행 | ‘영상 대신 현재 확인할 수 있는 화면으로 설명하겠습니다.’ |

미리 찍은 성공 영상은 유효한 예비 자료지만, 당일 live 성공의 증거로 바꾸지 않는다.

## 5. 심사위원 직접 체험

검증한 빌드와 합성 계정으로 시작한다. 실제 주문번호·개인정보를 입력하지 않도록 안내한다. 한 과제를 제시하고 원래 제공하는 UI 설명 외에 과도한 단계별 유도는 하지 않는다. 도움이 필요하면 제공한 도움을 기록한다.

질문 예시: ‘다음 행동이 무엇인지 찾을 수 있었나요?’, ‘제출 내용이 무엇인지 설명해 주실 수 있나요?’, ‘막힌 화면이 있었나요?’ 긍정 답변을 요구하지 않는다. 실제 답을 공개할지 별도 확인한다.

## 6. 재시연 준비

테스트 신청·예약 기록만 초기화한다. Chrome 비밀번호·개인 프로필·Keychain·인증 파일을 지우지 않는다. QA DB와 시연 DB를 분리한다. cold/warm 여부를 기록한다. 안정된 시연 폴더를 개발 작업자가 덮어쓰지 않게 한다.

구현할 `demo:start`, `demo:reset`, `demo:cold`, `demo:warm` 같은 이름은 기존 운영 문서의 역할 명세다. 실제 명령이 구현·확인되기 전에는 터미널에서 동작하는 명령으로 안내하지 않는다.
