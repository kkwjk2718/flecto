# Project FLECTO — 상세 Ralph Loop 운영 명세 v5

작성: 2026-09-28 · 행사 운영 시각은 2026-09-29 Asia/Seoul 기준

**문서 상태:** 실행 설계와 프롬프트·작업표·정책 참조 코드다. 제품을 구현한 결과나 실제 Claude/Codex 다중 실행·자동복구를 완주한 결과가 아니다. 이번 패키지에 실제 있는 도구는 `tools/check_plan.py`, `tools/policy.py`와 오프라인 정책 테스트다. 아래의 `supervisor`, `watchdog`, `demo:*`, `release:*`는 구현·리허설할 기능 명세이며 현재 실행 가능한 명령으로 간주하지 않는다.

## 1. 기준 문서와 바꾸지 않을 결정

제품 기준은 `reference/PRODUCT_v4_ORIGINAL.md`다. 원본은 수정하지 않고 보존했다. v5는 그 제품을 최소 개입으로 개발·검증·출고하는 운영 규칙을 추가한다. 작업 시간·슬롯·재시도 숫자는 이번에 제안하는 출발값이지 실측 생산성이나 완성 보장이 아니다.

개발은 Claude Opus 5.5를 요청 모델로 고정한다. 실제 계정에서 확인한 모델 ID를 사용하며 다른 코딩 모델로 몰래 전환하지 않는다. 같은 Opus 모델의 리드·구현·검토·QA 작업자는 여러 개 사용할 수 있다. Astra는 Codex를 통한 개발 이미지 제작에만 참여한다. 제품이 사용하는 Codex 런타임은 개발 에이전트와 별개다.

현장 장비는 사용자가 정한 14형 MacBook Pro M5 Pro, 24GB RAM, 1TB SSD다. Windows 네이티브 포팅이나 집 서버 필수 연결을 새 요구사항으로 넣지 않는다. 가재탈 조건을 우회하는 원격 조작도 제안하지 않는다.

제품은 구매 혜택 신청 A의 구조변형 B를 먼저 통과하고 같은 행사에서 문화센터 C로 확장한다. 고령자를 고려한 큰 글씨·큰 버튼, 공통 템플릿 6개, 원본 DOM 연결, Chrome 저장 테스트 계정 활용, DOM 우선/필요 시 안전한 시각 보완, 로컬 구조 캐시, 3초 목표/10초 종료, 3초 이후 준비 중 시연 후원카드를 유지한다. 자동 동의·대리 제출·실제 결제·CAPTCHA 우회는 하지 않는다.

## 2. 목표를 세 가지로 분리

**제품 목표:** 사용자가 새 화면에서 입력·선택·동의·제출하면 원본 서비스에 정확한 결과가 저장된다. 범위 B→C가 끝까지 작동한다.

**운영 목표:** 일상적인 함수명·구현 선택·오류 수정을 건우에게 묻지 않는다. 작업이 끝나면 다음 작업을 배정하고, 실패하면 정해진 정책으로 처리하며, 마감이 오면 검증된 결과를 보존한다.

**증거 목표:** 완료 여부는 에이전트의 말이 아니라 실제 실행한 검사, 원본 상태, 빌드 해시, 모델 실행 기록으로 판정한다. UI 성공 표시와 원본 저장 성공, fixture와 LIVE, warm 재사용과 cold 생성은 별도다.

‘사람 없이 계속한다’는 무제한 권한을 뜻하지 않는다. 인증·지출·외부 공개·실제 제출·안전사고는 별도 권한 경계다. 한번 사전 승인한 로컬 개발 범위에서는 질문 대신 기록하고 계속한다.

## 3. 세 계층과 권한

| 계층 | 책임 | 하지 않을 일 |
|---|---|---|
| 리드 Opus | 공통 계약, 우선순위, 모듈 배정, 최소 수정 전략 | 시스템 시계를 속이거나 테스트 통과를 선언만 하기 |
| Opus 작업자 | 자기 티켓의 코드 또는 검토·테스트 작성 | 공통 파일·다른 lane·감독자·자격증명 수정 |
| 결정적 감독 프로그램 | 상태, 임대·잠금, 프로세스, 병합, 실제 검사, 마감, 릴리스 | LLM 완료문을 증거로 믿거나 무한 재시도 |

개발자가 만든 감독 코드도 부트스트랩 검증 후 저장소 밖의 고정 control 디렉터리로 복사하고 해시를 고정한다. 그 이후 제품 코드 작업자가 실행 중인 감독 코드를 바꾸지 못하게 권한·도구 범위를 나눈다. 디렉터리를 나누는 것만으로 OS 보안이 확보되는 것은 아니다. 개발 전용 사용자/격리 환경, 최소 권한, 개인 데이터 없는 작업 환경이 별도로 필요하다.

메인 Opus는 판단의 소유자이고, 실제 프로세스 spawn과 슬롯의 소유자는 감독자 한 곳이다. 외부 감독자를 쓰면서 각 작업자의 ultracode/Workflow가 다시 무제한 하위 작업을 만드는 이중 증식은 금지한다. native subagent 모드를 쓰는 경우에도 동일한 task/lease/resource 등록이 실제로 검증되어야 한다. 기본 구현 경로는 감독자가 bounded `claude -p` 작업을 생성하는 방식이다. 이는 논리적으로 Opus 서브에이전트를 병렬 사용하는 것이며, 코딩 모델을 혼합하는 것은 아니다.

## 5. 출발 전 완료해야 하는 사전 점검

한 번 필요한 사람 단계: 대회 사전 준비·병렬 사용 규정 확인, 계정 로그인, 승인된 지출 범위 확정, 전용 작업 폴더와 시연 프로필 허용, 필요 OS/Chrome 권한 확인, 시작. 외부 제출은 마지막에 사람이 확인한다.

실행 점검표:

1. macOS/Node/Python/Git/Claude CLI/Codex CLI 버전과 설치 경로를 기록한다. 버전을 고정한 뒤 행사 중 자동 최신 업데이트를 루프에 넣지 않는다.
2. `claude auth status`, `codex login status` 같은 지원되는 상태 확인을 사용한다. 자격증명 파일 내용을 읽거나 프롬프트로 보내지 않는다.
3. 요청한 Opus의 실제 모델 ID로 짧은 작업을 실행하여 종료·출력·허용 도구를 확인한다. 모델이 다르면 통과가 아니다. 다른 모델로 fallback하는 설정이 없는지 확인한다.
4. 제품 Codex는 계정의 `model/list`와 기능 목록을 확인한다. 사용자 승인 범위의 후보만 간단히 평가하고 ID·effort·모달리티·SDK/CLI 버전을 잠근다. 목록이 있다고 실제 성공한 것은 아니므로 schema 반환 시험도 한다.
5. 이미지 위임 경로는 코드 변경이 없는 합성 에셋 한 개로만 확인한다. 미검증이면 asset 기능은 꺼두고 placeholder를 유지한다. 다른 유료 API로 임의 변경하지 않는다.
6. 테스트용 Chromium과 수용 테스트의 profile을 생성한다. 개인 Chrome 프로필을 자동 시험에 사용하지 않는다.
7. 실제 시연 Chrome 프로필에는 합성 테스트 계정만 저장하고, 원본 자동완성과 로그인 동작을 사람이 한번 확인한다. OS 암호/Touch ID 확인을 자동 우회하지 않는다.
8. planner와 두 원본 서버의 포트·루프백 접근·runtime 토큰·CORS/Host/Origin 처리를 검사한다. 포트가 점유되었다고 다른 사람의 프로세스를 종료하지 않는다.
9. 쓰기 경로, 네트워크 목적지, 설치 가능한 의존성·허용 명령을 좁혀 실제 작업 하나를 수행한다. 승인 범위 밖 작업은 무인 승인하지 않는다.
10. 네트워크 끊김·강제 종료·late handoff·마감·last_green 복구를 모의 프로그램으로 검사한다. 개발 시작 자체가 감독자 리허설을 대체하지 않는다.
11. 사용량·과금 경로를 확인한다. 구독의 예상 dollar cost를 실제 청구액으로 오인하지 않는다. 자동 추가 구매/계정회전/임의 API 전환은 금지한다.
12. 전원·절전·디스크·메모리 압력과 행사 시간대 설정을 확인한다. 화면 잠금이나 기기 재부팅 이후까지 무인 복구를 보장하지 않는다.

`config/preflight.template.json`에 증거 경로와 상태를 채운다. 비밀 값은 적지 않는다. 사전 점검이 미완료라면 live 실행을 허가하지 않는다. 해당 경로가 막혀도 이미 허용된 오프라인 검사나 문서 정리는 계속할 수 있다.

## 6. 자동화 준비가 본 제품 시간을 먹지 않도록

O01–O04는 감독자 구현·리허설 티켓이다. 사전 준비가 허용되면 행사 전에 끝내고 코드를 동결한다. 사전 제작이 제한되면 당일 허용 시점부터 작은 범위로 처리한다. 규정이 애매하다고 이미 구현했다고 가정하지 않는다.

대시보드 꾸미기·자체 에이전트 플랫폼·복잡한 ML 스케줄러·자동 계정관리·클라우드 오케스트레이션은 만들지 않는다. 필요한 것은 상태 보존, 제한 실행, 경로 검사, 직렬 병합, 실제 gate, 안전 종료뿐이다. 감독자 핵심 검사가 통과하지 않으면 ‘무인 모드 준비 완료’라고 선언하지 않는다. 그때 진행 가능한 범위와 막힌 이유를 분명히 표시한다.

기존 v2 engine은 혼합 모델·다른 폴더·이전 검사 ID·resume 미구현이 있으므로 모델명만 바꿔 실행하지 않는다. 부록 09의 호환성 목록으로 필요한 부분만 재사용한다.

## 7. 작업 표와 우선순위

`config/tasks.json`에 40개 초기 작업을 넣었다. 각 항목은 담당 lane, 의존성, 쓰기 경로, 수용 검사, 시간 상자, 자원, 우선순위를 가진다. 제품 v4 T01–T26은 `config/product-tests-v4.json`에 원문 기준으로 추출했다.

우선순위는 안전사고/개인정보 → 막힌 필수 gate → 임계 경로 → 독립 확장 → 속도 실험 → 외형 순이다. 임계 경로는 G0 최소연결, G1 첫 사이트, G2 구조변형, G3 두 번째 사이트, G4 전체검사, LIVE01, REL01이다.

같은 모델의 작업자도 역할을 분리한다. 연결기를 작성한 세션에 최종 보안 판단을 맡기지 않는다. 독립 검토자는 변경 사유보다 요구사항·diff·실제 실패를 먼저 읽는다. 같은 모델이므로 완전히 독립적인 검증자라고 과장하지 않고 프로그램 검사와 함께 사용한다.

태스크는 8분 소프트 경고/12분 하드 제한을 기본 출발값으로 둔다. 이 시간은 완성 예측이 아니라 한 작업에 자원을 묶어두는 상한이다. 너무 큰 작업은 기능 의미를 유지한 작은 티켓으로 나누며 요구사항 자체를 삭제하지 않는다. 수정은 최대 7분, 읽기 검토는 최대 5분, 리드의 배정 판단은 최대 3분을 출발값으로 둔다.

## 8. Opus 리드의 판단 시점

매 5초마다 리드를 호출하지 않는다. 감독자는 싸게 상태만 확인하고 다음 사건이 있을 때 리드에게 판단을 요청한다.

- 공통 계약을 처음 확정할 때.
- 구현 batch가 통합되어 다음 gate가 통과했을 때.
- 실패가 자동 분류되지 않거나 같은 원인이 반복될 때.
- 의존성 때문에 ready 작업이 없는데 미완료 필수 작업이 남았을 때.
- 범위 축소 또는 계약 마이그레이션이 필요할 때.

리드 입력은 제품 불변 조건, 현재 마감, gate 상태, 실패 요약, 최근 통합 diff, ready 후보와 자원 상황이다. 전체 대화·전체 원본 HTML·모든 로그를 매번 붙이지 않는다.

리드 출력은 task ID/owner/범위/이유/우선순위/필요검사만 담는 제한된 계획이다. 모델이 제안한 shell 명령을 그대로 실행하지 않는다. 등록된 작업과 명령의 범위를 프로그램이 검사한다. 산출물 형식이 틀리면 제한적으로 한번 고치고, 안 되면 해당 계획을 거부한다.

## 9. 티켓 생명주기

```text
WAITING → READY → RUNNING → PATCH_READY → CHECKING → INTEGRATED → VERIFIED
                         ↘ FAILED → bounded repair / BLOCKED / DEFERRED
                         ↘ INTERRUPTED → reconcile → new lease / QUARANTINED
VERIFIED → REVOKED (새 안전 결함이 발견된 경우)
```

`PATCH_READY`는 작업자가 끝났다고 보고한 상태다. `VERIFIED`는 supervisor가 정확한 후보에서 지정한 검사를 실행해 수락한 상태다. 이 둘 사이를 생략하지 않는다. 각 의존성은 필요한 contract를 구현·검사한 INTEGRATED 또는 gate VERIFIED 상태를 요구하도록 작업 종류별 규칙을 명시한다. 단순 worker 보고만으로 downstream을 시작하지 않는다.

티켓의 base_sha, contract_version, attempt, lease_generation, 실행 경로를 고정한다. 완료 handoff가 이 중 하나라도 다르면 late/stale 결과로 격리한다. 재시작 전의 에이전트가 늦게 결과를 쓰더라도 현재 작업을 덮어쓸 수 없어야 한다.

티켓 생성 시 입력과 기대 결과를 파일에 남긴다. 예: B01은 native 입력 어댑터와 검증만 작성한다. `packages/contracts/`, QA manifest, `ops/`를 고치지 않는다. T04/T06/T07 등 관련 검사와 자신의 단위 검사를 보고한다.

## 10. 파일 소유권과 worktree

쓰기 격리는 worktree, 실제 통합은 단일 작성자가 맡는다. worktree는 OS 샌드박스가 아니며 읽기·네트워크 권한을 제한해 주지 않는다. 공식 Claude 문서의 기본 branch 동작에 기대지 않고 supervisor가 각 worktree를 지정된 base_sha에서 생성하고 HEAD를 확인한다.

공통 타입·루트 package/lockfile·테스트 실행 명령은 contracts owner만 수정한다. 하위 경로도 잠금에 포함한다. `apps/extension/src/ui/` 소유자가 작업하는 동안 `.../ui/sponsor/`를 다른 작업자에게 동시에 주지 않는다.

공유 의존성을 바꿔야 하면 코드 작업자는 CONTRACT_CHANGE_REQUEST를 보낸다. 리드가 원래 ABI를 유지하는 최소 대안을 우선 판단하고, 정말 필요하면 해당 계약 사용자 작업을 일시 정지한다. 한 writer가 계약/lockfile을 변경하고 버전을 올린 뒤 관련 작업을 새 기준본으로 다시 배정한다. 늦은 옛 버전 결과는 자동 병합하지 않는다.

의존성 설치도 한 writer가 담당한다. 각각의 worktree가 무제한 설치/lockfile 변경을 하지 않는다. mutable node_modules 공유나 플랫폼이 다른 빌드 바이너리 재사용은 피하고, 검증된 패키지 매니저 캐시만 이용한다. lifecycle script를 무조건 전부 허용하거나 전부 막은 뒤 정상이라고 가정하지 말고, 선택한 도구에 필요한 설치 동작을 사전 검토한다.

## 11. 병렬 수 결정

기본은 리드 1개 + 구현 작업자 4개다. 리드 포함 코딩 모델 프로세스는 최대 9개(작업자 상한 8)지만 상한을 목표로 채우지 않는다. 초기 부트스트랩 때 ready 작업이 적으면 더 적게 실행한다.

작업자 완료 세 번이 아니라 **통합 후 검사까지 수락된 변경 세 번**을 기준으로 확대 여부를 본다. ready 작업이 충분하고, 병합 대기가 없고, 공급자 오류·메모리 압력이 없을 때 한 슬롯만 증가한다.

provider 제한 오류·메모리 압력·병합 대기 2개 이상이면 신규 배정을 줄이고, 출발안으로 현재 슬롯의 절반(최소 1)을 사용한다. 자원 측정을 할 수 없으면 보수적으로 초기 4개 이상 늘리지 않는다. 이 숫자는 휴리스틱이다.

build/의존성 설치/E2E/영상 렌더는 heavy 슬롯 1개를 공유한다. 단위 검사도 CPU·메모리가 큰 경우 heavy로 분류한다. 제품 LIVE 검사에는 product 슬롯도 필요하다. 이미지 작업은 1개, 제품 신규 계획은 1개이며 개발 worker 슬롯과 별도로 집계한다. 24GB Mac에서 코딩 프로세스 수만 보고 Playwright 8개를 같이 띄우지 않는다.

## 12. 실제 한 바퀴

1. 감독자가 현재 시간과 STOP, lock, 임대, 남은 사용량 정보의 가용성을 확인한다.
2. 종료된 작업의 로그·diff·handoff를 수거한다. 범위 밖 수정, 보호 파일 변경, symlink·경로 탈출·비정상 Git 이력을 거부한다.
3. 작업자의 검사는 참고자료로만 읽고 고정된 관련 gate를 supervisor가 실행한다.
4. 동일 base와 통합 HEAD 사이 변경을 확인한다. 충돌은 해당 owner에게 최소 수정 티켓으로 돌린다. 작업자들이 직접 서로 merge하지 않는다.
5. 후보 작업 공간에 한 batch를 순서대로 반영한다. 불완전한 작은 모듈은 계약 stub과 함께 단위 검사하고, 작동 가능한 세로 흐름이 만들어졌을 때 E2E gate를 실행한다.
6. gate 통과 후보만 안정 브랜치/증거에 등록한다. 실패 후보는 시연 경로로 보내지 않는다.
7. 필요한 경우 리드를 호출해 실패를 분류하고 다음 ready 작업을 선택한다.
8. 현재 마감에서 작업 하드 제한 + 관련 검사 + 되돌리기 시간이 들어갈 때만 새 작업을 시작한다.
9. source SHA·artifact hash·gate version·사용 모드를 상태 파일에 기록하고 반복한다.

마감은 루프의 마지막이 아니라 모든 단계 앞·뒤에서 검사한다. 멘토 피드백 반영 시에도 그 피드백이 사용자 새 결정인지 아이디어인지 구분하고, 제품 불변 조건을 몰래 바꾸지 않는다.

## 13. 게이트 세 단계

**로컬 관련 검사:** 작업자 변경 모듈의 타입·단위 검사. 결과를 믿고 바로 출시하지 않는다.

**통합 fixture 검사:** 실제 확장/원본 서비스/고정 모델 응답으로 T01–T26을 검사한다. 성공 문구가 아니라 실제 원본 값을 본다. 글로벌 오류, exit code nonzero, missing test, skipped, flaky, `.only`는 필수 통과가 아니다.

**실제 Codex 검사:** 실제 모델이 만든 계획으로 두 사이트를 각각 3회 이상 cold 실행한다. warm cache는 별도 검사한다. 전체 메뉴·페이지 이동에서 호출이 몇 번 필요한지 함께 기록한다. 최소 횟수만 채운 것은 통계적 신뢰 보장이 아니다.

릴리스는 같은 빌드 해시의 근거만 묶는다. 이후 제품 코드나 프롬프트·모델·설정·캐시 스키마를 바꿨으면 해당 검증은 다시 수행해야 한다. 완전히 동일한 파일 아티팩트를 재사용하고 변경이 제품에 영향 없는 문서뿐이라면 그 아티팩트 해시의 기존 근거임을 명시한다.

Playwright 확장 검사 환경은 번들 Chromium persistent context가 기본이다. 실제 Chrome password autofill은 별도 시연 프로필에서 추가 점검한다. QA가 개인 프로필이나 keychain을 가져다 쓰지 않는다.

## 14. 테스트를 고쳐도 되는 경우와 안 되는 경우

테스트를 삭제하거나 expected 값을 거짓 결과에 맞추는 것은 금지한다. 하지만 테스트 코드 자체가 잘못돼 무인 루프가 영구 정지하는 것도 피해야 한다.

테스트 결함이 의심되면 TEST_DEFECT 티켓을 만든다. 원본 T01–T26 의미는 그대로 두고, 별도 검토 Opus가 v4 문장·원본 직접 사용·실패 trace를 비교한다. 유효한 테스트 버그이면 QA owner만 수정하고 gate version을 올린다. 이전 검증은 영향을 받는 범위에서 무효화하고 회귀를 다시 실행한다.

이 권한은 사전 승인된 범위여야 한다. 요구사항을 더 약하게 바꾸는 판단이 필요하면 자동으로 테스트를 바꾸지 않는다. 모호한 경우 blocked를 기록하고 정상본을 보존한다.

불안정 테스트는 재시도해서 우연히 한 번 통과했다고 green으로 만들지 않는다. 원인을 고치고 다시 clean 실행한다. 실패 기록을 지우지 않는다.

## 15. 무응답·오류·재시도 정책

| 상황 | 자동 처리 | 사람 없이 넘지 않을 경계 |
|---|---|---|
| 요청이 잠시 막힘/서버 혼잡 | 제공된 Retry-After/오류 정보를 우선, 15·45초 범위의 제한 backoff | 한도 회피·다른 계정 교체 |
| 구독 quota 소진 | 확인된 reset이 마감 전이면 10분 간격 이하로 제한 확인, 아니면 확보 결과 검사·출고 | 유료 추가구매·다른 모델 자동 전환 |
| 인증 만료/모델 없음/과금 오류 | 해당 provider 경로 BLOCKED, 독립 오프라인 작업 유지 | 자동 로그인·지출 동의 |
| 단위/통합 테스트 실패 | 같은 실패는 최초 구현 후 수정 2회까지, 이후 새 Opus의 읽기 진단 | 동일 실패를 새 task ID로 위장해 무한 retry |
| merge 충돌 | 한 명이 최소 충돌 해결, 관련 검사 반복 | 무조건 theirs/ours, 기존 작업 삭제 |
| 의존성 설치 오류 | 같은 잠금 버전에서 제한 재시도·캐시 검사 | 최신 전체 업데이트·보안검사 제거 |
| 포트 점유 | supervisor 소유인지 확인, 소유한 테스트 인스턴스만 정리 | `killall node`/개인 Chrome 종료 |
| 이미지 실패 | 실패 상태 기록, placeholder 유지 | 앱 지연·자동 유료 provider 전환 |
| 민감정보 노출 의심 | 전송 중지, 관련 로그·캐시·릴리스 격리, 안전한 독립 작업만 유지 | 정상 사용으로 덮어쓰기 |

90초 도구 출력 없음은 진단 신호이지 무조건 실패가 아니다. 모델이 정상 추론 중일 수도 있다. heartbeat, 마지막 도구 상태, subprocess 상태, diff, 테스트 결과를 같이 본다. 4분간 유효한 진전이 없으면 진단하고, 작업 hard timeout 또는 절대 마감은 반드시 지킨다. 에이전트가 쓴 ‘계속 작업 중’ 텍스트만으로 무한 연장하지 않는다.

동일 버그의 세 번째 시도까지 실패하면 추가 구현을 자동 반복하지 않는다. 독립 진단은 되돌리기·범위 분리·후속 작업을 제안한다. 필수 안전 기능은 삭제하지 않는다. core blocker이면 제한적 결과임을 표시한다.

## 16. 감독자 자체 재시작과 lease

실행 상태는 SQLite를 진실의 원천으로 하고 JSON/HTML은 파생 표시로 만든다. 한 번에 supervisor 하나만 run.lock을 소유한다. task claim과 resource lease는 같은 트랜잭션으로 기록한다.

별도 얇은 watchdog은 supervisor 종료를 감시한다. 정상 종료·STOP·승인 필요 종료는 재시작하지 않는다. 비정상 종료일 때만 현재 마감 안에서 최대 2회 재시작을 시도한다. watchdog은 LLM을 직접 호출하지 않는다.

재시작 절차:
1. 단일 실행 잠금을 확보한다.
2. journal에서 마지막 정상 종료·마감·STOP를 확인한다.
3. RUNNING 작업의 PID뿐 아니라 생성 시각/작업 토큰/프로세스 그룹을 대조한다. PID가 같다고 다른 프로세스를 죽이지 않는다.
4. 소유 확인된 옛 프로세스만 정리하거나 관찰한다. 확인할 수 없는 것은 격리한다.
5. 미완성 worktree와 handoff를 보존한다. `git reset --hard`로 사용자의 기존 저장소를 초기화하지 않는다.
6. expired lease를 INTERRUPTED로 바꾸고 새 attempt·generation으로 필요한 작업만 배정한다.
7. 이미 통합된 patch/현재 HEAD를 확인해 중복 적용하지 않는다.
8. 마감 이후이면 코드를 다시 생성하지 않고 finalize한다.

중요: 개발 프로세스 재시작은 원본 웹사이트의 신청을 다시 실행하는 기능이 아니다. 제품의 pending source submit은 결과 확인 상태로 남기고 자동 재제출하지 않는다.

이 복구는 프로세스 크래시에 대한 설계다. Mac 재부팅·계정 잠금·전원 손실·네트워크 장애가 모두 자동 해결된다는 뜻이 아니다.

## 17. 실제 사람 개입을 최소화하는 결재 범위

자동 결정 가능: 함수명, 작은 화면 배치, typed 구현 대안, 같은 모델 안의 검증된 effort 조정, 이미 승인된 명령, 관련 오류 수정, 검증된 구조 재사용, optional 이미지 생략, 작업 수 축소, 검증된 정상본 선택.

조건부 자동: contract migration, 테스트 코드 버그 수정, 알려진 의존성 설치 재시도, 제한적 process 재시작. 반드시 owner·버전·근거·리그레션을 남긴다.

사람만: 인증/Touch ID·추가 결제·대회 규정 해석 변경·외부 배포/제출·실제 개인 계정 이용·개인정보 사고 대응 승인. 사용자에게 묻지 않기 위해 이런 권한을 이미 받은 척하지 않는다.

대시보드에는 `RUNNING`, `REPAIRING`, `WAITING_PROVIDER`, `BLOCKED_USER`, `FINALIZING`, `DEMO_READY`, `LIMITED`, `UNVERIFIED`를 구별한다. BLOCKED_USER인 동안 실행 가능한 독립 작업은 계속한다. 불필요한 ‘계속할까요?’는 금지하지만 필요한 승인을 숨기지 않는다.

## 18. 제품 성능 개선 루프

정확한 기준본이 먼저다. `ready_ms`는 사용 가능한 컨트롤의 검증 완료까지다. 빈 shell은 별도 `shell_ms`다. cold/warm/vision/timeout을 나눈다.

한 실험은 하나의 변경을 다룬다. 예: 페이지 문맥 축소, JSON 압축, 중복 호출 제거, 캐시 재연결 비용 감소, 지원 effort 조정. 가장 큰 병목을 실제 trace로 선택한다. 프로토콜 전체 교체나 새로운 인프라 구축은 뒤로 미룬다.

기능·보안 검사 → 동일 작업군 측정 → holdout → 변경 채택 순이다. 시도 수와 실패를 모두 남긴다. 실패한 10초 요청을 분모에서 빼거나 광고를 위해 시간을 늘리지 않는다. 모델/프롬프트 변경도 artifact 근거를 갱신한다.

당일 속도 실험은 최대 2회 출발값으로 제한한다. 3초가 안 되면 10초를 숨기거나 요구사항을 속이지 않고 실제 측정값을 발표한다. 속도를 위해 필수 설명·확인·검증을 없애는 것은 금지한다.

## 19. 이미지와 광고의 비차단 처리

광고는 제품 기능이고, 그 광고용 이미지 제작은 선택적인 개발 에셋 작업이다. 이미지가 없으면 텍스트·기본 정적 카드로 광고 동작을 검사할 수 있다.

Claude가 request.json을 작성하고 asset broker만 Codex/Astra 이미지 경로를 호출한다. 원본 소스·토큰·제품 사용자 데이터는 주지 않는다. image job은 작업별 폴더에서 결과 파일·형식·크기·status를 반환한다. 프롬프트를 응답한 것은 이미지 완성이 아니다. 파일을 실제 열어 확인하고, 승인된 산출물만 integrator가 복사한다.

job 하나씩 실행, 한 생성+수정 1회 이내, 13:30 신규 요청 중단, 14:45 검토·반영 종료를 출발안으로 한다. 실패해도 앱을 막지 않는다. 세션·model settings·user profile을 image worker가 자동 변경하지 않는다.

제품에서 광고는 준비 중 3초를 넘을 때만, 한 goal session에 최대 1회다. READY/취소/10초 만료와 동시에 사라진다. 광고 최소 노출 시간을 만들지 않는다. 시연 광고는 실제 후원·수익으로 기록하지 않는다. 광고에 private DOM/goal/URL을 전달하지 않는다. 원본 v4 T15–T20으로 검증한다.

## 20. 시간표와 시간에 따른 기능 축소

절대 마감은 config에 timezone과 함께 기록하고 프로세스 hard timeout은 monotonic clock으로도 검사한다. 일정은 내부 운영 기준이며 현장 규정이 다르면 실행 전에 바꾼다.

| 시각 | 운영 목표 / 강제 정책 |
|---|---|
| 행사 시작 직후 | 사전 점검 결과 확인, contracts·최소연결·실제 Codex probe. 준비가 안 된 상태를 숨기지 않음 |
| 11:15~12:00 목표 | G0/G1 첫 사이트 end-to-end. 아직 안 되면 이미지·문서 미화 작업보다 연결기 우선 |
| 12:00~13:30 목표 | 구조변형 B·캐시·오류·시간 상한. 독립 문화센터 원본 제작 병행 |
| 13:30 | 신규 이미지 요청 금지 |
| 13:30~14:20 목표 | 문화센터 C 제품 연결, 두 사이트 회귀, 실제 모델 근거 |
| 14:20 | 큰 신규 feature 티켓 금지. 이미 진행한 필수 기능만 닫기 |
| 14:45 | 기능 동결. 새로운 동작 추가보다 기존 기능 오류·품질 수정만 |
| 15:35 | 제품 코드 변경과 개발 LLM 호출 종료. 실행 중 작업도 보존 후 종료 |
| 16:05 | 패키지·근거 확정. 이 뒤에는 확정된 시연 빌드만 사용 |
| 16:30 | 제출 목표. 실제 제출은 사람이 확인 |

시간을 늦게 시작했다고 자동으로 행사 마감을 뒤로 미루지 않는다. 배정 조건은 작업 hard budget + 관련 gate budget + rollback reserve가 freeze 안에 들어가는가다. 예를 들어 15:25에 7분 수정과 8분 검사, 2분 되돌리기가 필요하면 새 수정을 시작하지 않는다.

빼는 순서는 추가 장식/영상 확장 → 선택 에셋 → 불필요 설정 → 속도 실험 → 추가 변형 수다. 두 번째 사이트는 목표로 유지하되 검증되지 않으면 단일 사이트 한계를 공개한다. 개인정보·동의·중복/unknown·10초·원본 복귀는 범위 축소로 삭제하지 않는다. v4 기준의 FULL 출고 요건을 줄여놓고 FULL이라고 표시하지 않는다.

## 21. 정상본 보존과 등급

| 등급 | 의미 |
|---|---|
| FULL_LIVE | 같은 artifact에서 T01–T26 전체 fixture 통과 + 두 사이트 각 실제 cold Codex 흐름 3회 이상 + 원본 결과 확인 |
| SINGLE_SITE_LIVE | 구매혜택에서 원본 저장과 관련 안전검사·실제 Codex를 확인. 두 번째 사이트는 미완성이라고 표시 |
| FIXTURE_ONLY | 코드 회귀는 확인했으나 실제 제품 모델 연결·완주를 입증하지 못함 |
| UNVERIFIED | 출고 검사 근거 부족. 완료 제품으로 시연하지 않음 |
| REVOKED | 이전 green에도 안전 결함이 확인되어 사용 금지 |

FULL의 live 반복은 warm cache로 대체하지 않는다. source가 다르거나 모델/빌드가 다른 결과를 합산하지 않는다. release를 선택할 때 안전이 확인된 높은 등급을 우선하고, 그 안에서 최신 검증본을 택한다. 어제 통과했더라도 새로 발견한 보안 문제가 적용되는 버전이면 폐기/격리한다.

last_green 하나만 유지하지 말고 단계별·artifact별로 이력을 남긴다. 개발 repo 최신 HEAD와 시연 artifact를 분리한다. 시연 중인 배포 폴더·DB를 worker가 덮어쓰지 않는다.

## 22. 시연·reset·패키징

최종 산출물: 확장 빌드, planner·두 데모 서비스의 실행 파일/잠금 의존성, 실제 테스트·live 근거, 원본 v4 및 변경 사양, 모델잠금 정보, metric 보고서, 발표 대본, 예비 영상, 한계 목록, 릴리스 manifest.

절대 넣지 않을 것: 개인 Chrome 프로필, 저장 비밀번호, auth.json·토큰·세션 쿠키, 실제 사용자 입력, 전체 사적인 대화 로그, 불필요 원본 캡처. 로그는 개인정보 sentinel 검사도 하고 사람이 볼 설명에는 근거 있는 집계만 사용한다.

demo reset은 합성 신청·예약 상태만 바꾸고 비밀번호 저장·개인 폴더·Chrome 프로필은 지우지 않는다. QA profile과 시연 profile, QA DB와 demo DB, worktree port와 안정 서비스 port를 나눈다. 검사 끝에 task가 만든 프로세스만 정리한다.

5장면: 원본 메뉴 → 큰 화면 → 원본 저장 → 준비된 화면에서 계획 endpoint만 차단 → 두 번째 사이트/구조 무효화. 인터넷 전체를 끄는 시연으로 혼동하지 않는다. 광고 시연에 주입 지연을 쓰면 fault injection임을 표시한다.

발표 초안은 기능이 돌아가기 시작하면 별도 Opus가 일찍 준비한다. 실제 수치 자리는 비워두고 마지막 finalizer가 결과 JSON으로 채운다. 마지막에 모델 한도가 소진돼도 보고서를 만들 수 있게 한다. UI截图·영상에 fixture 문구를 지워 live처럼 보이게 하지 않는다.

## 23. dashboard에 보여줄 정보

현재 단계, 다음 절대 마감, active/ready/blocked 작업 수, 통합 대기 수, 마지막 통과 artifact, 제품모드, 최근 gate 실패, product/provider 상태, 알려진/미확인 사용량, 사용한 모델, 이미지 대기, blocker와 자동 대체 행동을 표시한다.

‘전체 83% 완료’ 같은 LLM 추정치 대신 `G2 PASS / G3 RUNNING / T 21 PASS·3 FAIL·2 NOT RUN / LIVE benefits 1, culture 0`처럼 검사 가능한 정보를 쓴다. 숫자는 실제 실행 결과가 있을 때만 넣는다. 단계별 결과와 작업 시간이 인위적인 진행률을 대체한다.

## 24. 감독자 운영 수용 검사 O01–O15

이것들은 앞으로 실제 프로세스를 가지고 수행할 운영 테스트다. 이번에 실행한 순수 정책 테스트 49개와 다르다.

| ID | 주입 상황 | 기대 동작 |
|---|---|---|
| O01 | supervisor 두 번 시작 | 두 번째가 같은 run을 획득하지 못함 |
| O02 | code_stop 경계 | 새 코딩 시작 안 함, 남은 자식만 안전 종료 |
| O03 | 작업 중 감독자 종료 | ledger 기반 복구, 정상본 보존 |
| O04 | 옛 worker의 늦은 결과 | lease generation 불일치로 격리 |
| O05 | 복구 후 동일 patch | 중복 merge하지 않음 |
| O06 | worker 무응답 | 제한 후 종료·수정 정책, 무한 대기 없음 |
| O07 | 429/인증/한도 | backoff·BLOCKED·reset 분리; 자동 결제 없음 |
| O08 | PID 재사용·타인 포트 | 소유 미확인 프로세스를 죽이지 않음 |
| O09 | 보호 파일 수정 | patch 거부, 고정 gate·사양 유지 |
| O10 | 누락/skip/flaky report | 전체 통과로 판정하지 않음 |
| O11 | 다른 빌드의 LIVE 근거 | 현재 release의 LIVE로 인정하지 않음 |
| O12 | gate 실패 후 마감 | 정상본 또는 정직한 제한 등급으로 패키지 |
| O13 | 이미지 실패·늦은 도착 | 앱 진척/시연 유지, freeze 이후 자동 반영 안 함 |

| O15 | STOP·비정상·정상 종료 | STOP/정상은 restart하지 않고 crash만 제한 재시작 |

## 25. 현재 패키지의 검증 경계

실제 작성한 것은 작업 DAG/정책/스키마 예시/프롬프트/세부 운영 문서와 오프라인 순수 정책 코드다. 정책 코드의 경로·시각·상태·release eligibility·재시도·자원 판단은 단위 테스트했다. 이것은 사용자 계정·CLI·macOS process control·Chrome 입력·모델 성공·실제 메모리 부하·안전 격리를 검증하지 않는다.

제품 v4의 26개 테스트는 보존했지만 여기서 실행하지 않았다. O01–O15도 실프로세스 시험 계획이다. 완전 무인 완주, 정해진 시간 내 FULL 완성을 보장하지 않는다. 다만 완료를 꾸며내거나 끝없이 대기하지 않도록 구현할 판단을 명시했다.

공식 도구 사실과 새 설계 판단은 구분한다. 외부 문서 확인은 `08_SOURCES.md`에, 원본 제품은 `reference/PRODUCT_v4_ORIGINAL.md`에 있다. Notion의 예전 문서를 이번 작업에서 변경하지 않았다.
