# 제품 개발을 막지 않는 발표·홍보 작업 연결

**v7 추가 작업 계획. 기존 40개 제품·운영 작업 DAG는 수정하지 않는다.** 아래 COM 작업은 문안·발표 패키지를 위한 독립 편집 작업이다. 발표 완료가 제품 첫 연결이나 안전 검증의 선행조건이 되지 않는다.

## 역할과 범위

COMMUNICATION_LEAD는 `presentation/`, `marketing/`, `business/`, 발표용 `evidence/` 문안을 관리한다. 개발 모델명은 고정하지 않는다. QA는 실제 제품·원본 결과와 빌드 근거를 제공하고, RELEASE는 결과·라벨·한계를 최종 대조한다. 발표 담당이 제품 코드·테스트 결과·상태를 성공으로 바꿀 수 없다.

| COM03 차트 도형 준비 | COM01 | A–H 중 선택한 개념도·빈 결과 자리 | 가짜 수치·우열·계약 로고 없음 |

| COM06 예비 영상·Q&A 리허설 | 실제 캡처가 있을 때, 영상은 선택 | 녹화 라벨·실패 대응·질문 답 | 실제 데이터·공개 범위 확인 |
| COM07 최종 패키지 점검 | 가용 자료 전부 | 발표·대본·한계·실제 상태 기록 | 공개 점검표, 사용자 제출 확인 |

## 일상 루프

기존 spec과 실제 빌드 상태 읽기 → 현재 허용 주장 선택 → 문안/도형 준비 → 실제 근거 붙이기 → 독립 검토 → 상태 갱신. 제품 실패가 생기면 슬라이드의 성공 주장을 수정하지 제품 검사를 약화하지 않는다.

## 자원·마감

문서 작성은 제품 핵심 작업의 모델 사용량을 소진하지 않는 범위에서 진행한다. 이미지·영상은 선택 사항이다. 무거운 렌더는 기존 heavy 슬롯을 공유하고 브라우저 검사보다 우선하지 않는다. 15:35 이후 개발 호출 중단이라는 기존 기준을 임의로 무시하지 않는다. 최종 정리는 미리 준비한 문안과 실제 결과로 처리한다.

## 노션·외부 공유

이번 폴더가 생성됐다고 노션이 업데이트되거나 외부 링크가 공개된 것은 아니다. 사용자가 요청한 경우에만 별도 읽기·쓰기·검증 절차로 옮긴다. 실제 제출 확인이 없으면 submitted=false다.
