# Ralph Loop v6 — 모델 비종속, 제품 우선, 최소 개입

## 목적

사람이 반복해서 '다음 구현', '테스트', '고쳐', '이제 멈춰'를 말하지 않아도 승인된 작업 범위 안에서 진행한다. MD는 실행 프로그램이 아니므로 실제 클라이언트가 읽고, 필요한 제어 코드는 구현·검사해야 한다. 무한 권한·무한 호출·완주 보장이 아니다.

## 1. 실행 경로 선택

**SESSION_LOOP:** 현재 코딩 클라이언트의 실제 지원 기능으로 작업을 진행한다. 순차 작업 또는 검증된 네이티브 서브작업, 검사 스크립트, 체크포인트를 사용한다. 별도 크래시 복구를 검증하지 않았다면 세션 밖 자동 재개는 주장하지 않는다.

**MANAGED_LOOP:** 지원되는 비대화형 실행 인터페이스와 최소 감독 코드가 실제 fault test를 통과한 뒤 사용한다. 상태·작업 임대·시간·프로세스·통합·검사를 바깥 프로그램이 맡는다. 네이티브 worker가 다시 무제한 worker를 만드는 이중 증식은 금지한다.

**SERIAL_SAFE:** 병렬 격리를 확인하지 못했거나 자원이 부족하면 같은 기준으로 한 작업씩 진행한다. 새로운 클라이언트를 임의 설치하거나 유료 모델로 바꾸지 않는다.

운영 등급과 제품 등급은 분리한다. MANAGED 준비가 늦어도 제품 첫 연결은 기다리지 않는다. 안전한 경로가 전혀 없다면 제한 상태를 기록하되 가능한 비실행 문서 작업은 유지한다.

## 2. 첫 작업의 우선순위

E00 읽기점검 → E01 승인된 환경 → C01 계약. D01 원본 사이트·X01 추출·V01 검증·U01 템플릿·N01 메시지·PF01 fixture seam을 병행한다. P01 실제 Codex 연결도 일찍 확인하지만 **P01 미완료가 I00/G00의 fixture 연결을 막지 않는다.**

OPS01은 최소 상태·제한 실행·결과수집만 한다. 자체 웹 대시보드·완전한 agent 플랫폼·새 메시지 큐·서버 클러스터 제작은 하지 않는다. 이미 클라이언트가 제공하는 일을 다시 구현하지 않는다.

## 3. 한 바퀴의 이벤트 루프

1. STOP·현재 모드·절대 마감·권한·리소스를 읽는다.
2. 끝난 작업의 task/attempt/lease/base/contract와 실제 diff를 확인한다.
3. 범위 밖 수정·보호파일·경로탈출·오래된 결과를 거부한다.
4. 후보 worktree에 단일 작성자가 순서대로 반영한다.
5. 변경 모듈 검사와 필요한 stage gate를 실제 실행한다.
6. exit code·시험 목록·원본 oracle·빌드 해시를 검증한다.
7. 통과 결과를 stage별 검증본으로 보존하거나 실패를 분류한다.
8. ready 작업이 있고 시간·권한·잠금이 허용하면 다음 티켓을 배정한다.
9. 상태 요약과 NEXT_ACTION을 갱신한다.

모든 이벤트에 리드 LLM을 호출하지 않는다. 계약결정, 다음 단계 배정, 원인불명 실패, 의존성 정체, 범위조정 때만 판단을 요청한다. 단순 heartbeat·시계·프로세스 조회는 코드가 한다.

## 4. 작업 선정

안전사고 차단 → 현재 필수 흐름의 blocker → 먼저 완성 가능한 세로 흐름 → 구조변형 B → 문화센터 C → 품질·성능 → 장식 순이다. ready는 선행 티켓이 필요한 수준으로 통합·검증되고 계약이 현재라는 뜻이다. worker의 완료 문구만으로 선행 충족 처리하지 않는다.

두 번째 원본 사이트는 독립적으로 일찍 만들 수 있다. 반면 QA의 첫 사이트 변형은 두 번째 사이트가 끝나기를 기다리지 않는다. 원본 서비스·QA·제품 planner를 불필요하게 결합하지 않는다.

## 5. 병렬성

설치·계약 단계는 직렬. 신규 환경은 worker2로 시작하고 통합 정상 이후 4로 올린다. 상한8은 목표가 아니라 안전 상한이다. accepted patch 3개 연속, 충분한 ready 작업, 통합대기 없음, 사용량/메모리 문제 없음일 때만 한 슬롯 증가한다.

통합대기2 이상, 공급자 rate 오류, 메모리 압력, 브라우저 불안정이면 신규 배정을 줄인다. 자원 측정이 없으면 4 이상 늘리지 않는다. 롤백·검사할 시간이 부족하면 새 작업을 시작하지 않는다.

heavy(설치/큰build/E2E/영상)는 전체1, 제품 추론1, 이미지1이다. 읽기 검토와 가벼운 단위 검사는 가능하지만 실사용 메모리를 보면서 줄인다. 검사 프로필·포트·DB를 동시에 공유하지 않는다.

## 6. 한 티켓의 출발 제한

일반 구현 soft8분/hard12분, 작은 수정7분, 읽기검토5분, 배정판단3분을 초기 자원 상한으로 둔다. 이것은 결과가 그 시간 안에 나온다는 약속이 아니다. 충분한 gate/rollback 시간이 없으면 더 짧은 독립 작업을 고르거나 종료한다.

이벤트 출력이 잠깐 없다고 죽이지 않는다. 90초 무출력은 진단 신호, 4분 유효 진전 없음은 분류 신호다. 실제 diff·도구·프로세스·타임아웃을 함께 본다. '계속하고 있다'는 문구로 무한 연장하지 않는다.

## 7. 피드백·수정

실패 서명은 요구사항ID+재현상태+stack/원본 결과+계약버전으로 묶는다. 초기 구현 뒤 같은 원인 수정2회까지만 허용하고, 이후 새 검토 세션이 최소 재현으로 원인을 분류한다. 새 task ID로 무한 시도 횟수를 초기화하지 않는다.

옵션 기능을 뺄 수는 있지만 필수 동의·개인정보·중복제출·10초종료·원본복귀를 '범위 축소'로 삭제하지 않는다. 테스트 자체 오류는 독립 QA의 원문 비교와 version bump로 수정할 수 있다. 제품 결과에 expected를 맞추지 않는다.

## 8. 성능·광고

성능 loop는 정확한 기준본 이후만 시작한다. 실제 controlsReady를 측정하고 가장 큰 병목 하나를 수정해 원래 검증과 holdout을 반복한다. 광고는 준비 상태의 관찰자이지 scheduler의 보상 항목이 아니다. 광고 시간을 늘리기 위해 cache hit를 막거나 대기를 추가하지 않는다.

## 9. 사람과의 소통

사용자에게는 현재 단계·실제 완료·차단·다음 마감만 알려준다. 일반적인 시행착오 승인 질문은 하지 않는다. 새 인증·지출·규정·실제 외부 동작은 한 묶음으로 질문하고 해당 경로만 BLOCKED로 둔다. 중요한 새 위험이나 권한 변경은 숨기지 않는다.

자율화는 사용자 장비에 실제로 켜진 클라이언트/프로세스의 기능이다. ChatGPT 메시지가 종료된 뒤 이 문서가 스스로 개발한다고 말하지 않는다.

## 10. 마감

실제 실행 설정을 따른다. 기존 내부 기준은 13:30 이미지신규중단, 14:20 큰 신규작업중단, 14:45 기능동결, 15:35 코드·개발모델중단, 16:05 패키지확정, 16:30 제출목표다.

작업 hard budget + gate budget + rollback reserve ≤ 남은 허용 시간이어야 한다. feature는 featureFreeze까지, repair는 codeStop까지 검사 포함해 끝낼 수 있어야 한다. cutoff에 도달하면 늦은 patch를 적용하지 않는다. finalizer는 코드개발이 막혀도 확보 자료로 등급과 한계를 출력한다. 제출은 사람이 확인한다.
